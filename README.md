# Provenance Guard

A Flask backend for reviewing the possible origin of creative text. It combines
Groq's semantic assessment with independent structural measurements, returns a
plain-language transparency label, and lets creators contest a decision. The
result is a fallible assessment of writing, **not proof of authorship**.

Implemented: text submission, two detection signals, confidence with an uncertain
range, three transparency labels, persistent appeals, submission rate limits, and
structured SQLite audit logging. No optional stretch features are claimed.

## Run locally

Requires Python 3.10+ and a Groq API key. Tested with Python 3.13.7.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

On a **fresh clone**, create the local configuration:

```bash
cp .env.example .env
```

Replace `your_key_here` in `.env` with your Groq key, then run:

```bash
flask --app app run --port 5001
```

Use port 5001 to avoid macOS services that sometimes occupy port 5000. Restart the
server after editing `.env`. `GET /health` reports whether a key is configured,
without exposing it. A missing/invalid key or provider outage still lets the API
run, but results are explicitly degraded and uncertain.

The default model is `openai/gpt-oss-120b`. The course's suggested Llama 4 Scout
model was retired on July 17, 2026; Groq recommends this replacement in its
[deprecation notice](https://console.groq.com/docs/deprecations). Set `GROQ_MODEL`
in `.env` to override it. The detector uses
[Groq JSON object mode](https://console.groq.com/docs/structured-outputs) and
validates the returned score and explanation itself.

Only the source, tests, dependencies, example configuration, README, and plan are
submission files. `.env`, `.venv`, Python caches, and the generated `instance/`
database/evidence are ignored. No API keys or runtime databases belong in Git.

## Architecture

See the two-flow diagram in [planning.md](planning.md#architecture), written
before implementation. The code is split by responsibility:

- `app.py`: Flask app factory, input validation, endpoints, and rate limits.
- `detection.py`: Groq assessment, structural measurements, scoring, and labels.
- `storage.py`: SQLite content, appeals, and transactional audit events.
- `test_app.py`: deterministic tests, including the four course sample texts.

A submission passes through IP rate limiting and JSON validation. Groq assesses
the text semantically, and a separate Python function measures its structure.
The scorer weights these results, reduces confidence when they disagree, applies
insufficient-evidence guards, and chooses the transparency label. SQLite saves
the content and a structured decision event in the same transaction; the response
then returns the saved UUID, attribution, confidence, signals, label, and status.

An appeal looks up that UUID, checks the supplied creator ID, saves the creator's
reasoning, changes the content to `under_review`, and appends an event carrying
the original decision. The original attribution, scores, label, and decision
timestamp remain intact. The review queue exposes the original text and evidence
alongside the appeal for a human reviewer.

## API and quick demonstration

- `POST /submit`: `text` and `creator_id`; returns 200 and the saved decision.
- `POST /appeal`: `content_id`, `creator_id`, and `creator_reasoning`; returns 201.
- `GET /content/<content_id>`: current decision and any appeal, or 404.
- `GET /appeals`: up to 100 pending reviews, oldest first.
- `GET /log?limit=20`: newest audit events; limit must be 1–100.
- `GET /health`: local service/configuration check; no remote inference call.

Text must contain 1–20,000 characters after trimming; creator IDs must contain
1–100. Appeal reasoning must contain 10–4,000 characters. Missing/wrongly typed
fields and invalid JSON return 400; non-JSON submissions return 415; bodies over
96 KiB return 413. These invalid inputs never invoke detection or create a
decision event. Rate-limited requests return JSON 429 with `Retry-After`.

With the server running, submit this deliberately AI-authored test passage:

```bash
curl -sS -X POST http://127.0.0.1:5001/submit \
  -H 'Content-Type: application/json' \
  -d '{"creator_id":"demo-writer","text":"As an AI language model, I do not have personal experiences, emotions, or memories. As an AI language model, I can provide a comprehensive overview of the topic. As an AI language model, I cannot independently verify the experiences described by human users. In conclusion, this response was generated by an artificial intelligence assistant to provide general information. It is important to note that this response should be reviewed for accuracy and completeness."}' \
  > /tmp/provenance-guard-submission.json
python -m json.tool /tmp/provenance-guard-submission.json
```

Extract the returned ID and appeal it. This is a workflow demonstration, not a
claim that the AI test passage is human-written:

```bash
CONTENT_ID=$(python -c 'import json; print(json.load(open("/tmp/provenance-guard-submission.json"))["content_id"])')
curl -sS -X POST http://127.0.0.1:5001/appeal \
  -H 'Content-Type: application/json' \
  -d "{\"content_id\":\"$CONTENT_ID\",\"creator_id\":\"demo-writer\",\"creator_reasoning\":\"Demo appeal: please review the original text and my explanation.\"}" \
  | python -m json.tool
curl -sS "http://127.0.0.1:5001/content/$CONTENT_ID" | python -m json.tool
curl -sS http://127.0.0.1:5001/appeals | python -m json.tool
curl -sS 'http://127.0.0.1:5001/log?limit=3' | python -m json.tool
```

The appeal response and subsequent content lookup show `status: "under_review"`
and `appeal_filed: true`. A repeated appeal returns 409, an unknown content ID
returns 404, and a different creator ID returns 403. Duplicate/concurrent appeals
cannot overwrite the existing reasoning or create a second event.

**Identity and access scope:** this classroom API matches a caller-supplied creator
ID; it does not authenticate people. Someone who knows that ID can impersonate
them. `/log`, `/content`, and `/appeals` are unauthenticated inspection endpoints
for local grading; the review queue includes submitted text. A deployed platform
must authenticate creators, restrict reviewer/admin routes, and apply retention
and privacy controls. No automatic penalties or content removal are implemented.

## Detection signals

**Groq semantic assessment — 70%.** The model considers context, specificity,
generic rhetoric, and coherent stylistic patterns. It returns `ai_score` in [0, 1]
and an explanation. This supplies meaning/context that simple counts miss. The
prompt explicitly treats submitted text as untrusted data and warns against
equating formal or non-native writing with AI. JSON parsing, numeric bounds,
finite-number checks, and required explanations prevent malformed responses
from becoming decisions. Requests time out after 20 seconds without SDK retries.

Its blind spots include prompt injection, model bias, edited/mixed authorship,
memorized literature, and convincing imitations. JSON validity is not factual
validity. Exceptions or missing credentials produce `available: false` and a null
model score; no synthetic replacement is represented as a Groq result.

**Stylometric structure — 30%.** Pure Python measures sentence-length coefficient
of variation (standard deviation divided by mean), vocabulary diversity
(unique/total words), and punctuation characters per word. It captures structural
regularity without asking another model. Sentence uniformity receives most of
this signal's weight; diversity and punctuation are deliberately weaker proxies.

```text
uniformity  = clip(1 - sentence_length_cv / 0.8)
vocabulary  = clip((0.9 - type_token_ratio) / 0.5)
punctuation = clip(1 - punctuation_per_word / 0.3)
stylometry  = 0.75*uniformity + 0.15*vocabulary + 0.10*punctuation
```

`clip` restricts a component to [0, 1]. The response records the raw metrics and
component scores. Repetitive poetry and carefully edited academic prose can look
machine-like; irregular AI writing can look human. Sentence splitting is a simple
punctuation/newline heuristic, so abbreviations, decimals, and verse are difficult.
Type-token ratio changes with passage length. These are heuristic assumptions,
not established signatures of AI. The two signals measure different properties
but are not statistically independent.

## Confidence scoring and validation

`confidence` is an **AI-support index** (`score_kind: "ai_support"`), not a
calibrated probability. A high score means stronger AI-like evidence; a low score
means stronger human-like evidence. Thus 0.1840 is human-leaning, not "18.4%
confidence that the verdict is correct." A score near 0.5 means little useful
directional evidence. In particular, 0.51 and 0.60 remain uncertain, while 0.95
produces the strong AI label when no insufficient-evidence guard applies.

```text
raw = 0.70*llm_score + 0.30*stylometric_score
agreement = 1 - 0.5*abs(llm_score - stylometric_score)
confidence = 0.5 + (raw - 0.5)*agreement
```

Disagreement pulls the score toward 0.5. With fewer than 40 words **or** fewer
than 3 sentences, clamp it to [0.35, 0.65]. Without Groq, use only the explicitly
degraded index `0.5 + 0.25*(stylometric_score - 0.5)`, limited to [0.375, 0.625].
Both situations always remain uncertain. Round to four decimals, then label:

- `confidence >= 0.85`: `likely_ai`.
- `confidence <= 0.20`: `likely_human`.
- Otherwise: `uncertain`.

The stronger AI threshold and wide middle range reflect the greater harm of
falsely accusing a human writer. The 70/30 weighting gives holistic assessment
more influence than fragile structural proxies, while requiring consistent
support for a strong label. These thresholds are a design choice; they have not
been fitted to a representative, independently labeled dataset.

### Actual live examples

The following results were captured on November 17, 2026 using real Groq calls to
`openai/gpt-oss-120b`, not mocked model scores. Model results may change on reruns.

1. **High AI support:** the full AI boilerplate passage in the curl example above
   returned LLM **0.92**, stylometry **0.820506**, combined **0.8707**,
   `likely_ai`. It was generated for this project's test, so its origin is known.
2. **Lower AI support / uncertain:** the course's casual ramen passage below
   returned LLM **0.20**, stylometry **0.254888**, combined **0.2242**,
   `uncertain`. It leans human but narrowly misses the conservative human cutoff.

   > ok so i finally tried that new ramen place downtown and honestly? underwhelming. the broth was fine but they put WAY too much sodium in it and i was thirsty for like three hours after. my friend got the spicy version and said it was better. probably won't go back unless someone drags me there

3. **High human support:** the opening paragraph of Poe's public-domain
   [The Tell-Tale Heart](https://www.eapoe.org/WORKS/reading/pt043r1.htm) returned
   LLM **0.15**, stylometry **0.223265**, combined **0.1840**, `likely_human`.
   This is a known human work, but the model may recognize it from training;
   that makes it a weak test of performance on unseen human writing.

All four course samples were also submitted live:

- Course AI paragraph: LLM **0.78**, stylometry **0.460539**, combined **0.6547**,
  `uncertain`.
- Course human-style ramen paragraph: **0.20 / 0.254888 / 0.2242**, `uncertain`.
- Formal monetary-policy paragraph: **0.60 / 0.606531 / 0.6016**, `uncertain`;

not detector accuracy, empirical calibration, or reliable detection of editing.

## Transparency labels — exact text

**High-confidence AI (`likely_ai`):**

> "Likely AI-generated. Both checks strongly suggest AI involvement, but this is not proof. The creator can appeal."

**High-confidence human (`likely_human`):**

> "Likely human-written. Both checks suggest human authorship, but this is not verification of who wrote it."

**Uncertain (`uncertain`):**

> "Authorship uncertain. There is not enough consistent evidence to distinguish human writing from AI-generated text. No conclusion should be drawn."

These strings exactly match `detection.LABELS` and the labels in planning.md.
An appeal adds the separate `under_review` status; it does not silently relabel
the original decision. A verified-human credential is not implemented.

## Rate limiting and observed evidence

`app.py` commits the configuration `SUBMISSION_LIMITS = "10 per minute;100 per
day"`, keyed by direct source IP, with Flask-Limiter's `storage_uri="memory://"`.
Ten per minute accommodates a short revision burst; one hundred per day permits
active writers while placing a bound on inference costs. An IP key prevents
trivially bypassing the quota by changing a submitted creator ID. Appeals have a
separate ten-per-minute IP limit to protect the review queue.

Every attempt counts, including invalid requests. Blocked requests stop before
Groq and do not create attribution events. Counters reset on process restart and
are not shared across workers; shared networks can unfairly share a quota. A
production service should use shared Redis, authenticated per-creator quotas,
and a deliberately configured trusted proxy. See the
[Flask-Limiter configuration documentation](https://flask-limiter.readthedocs.io/en/stable/configuration.html).

On a fresh server, run:

```bash
for i in $(seq 1 12); do
  curl -s -o /dev/null -w '%{http_code}\n' \
    -X POST http://127.0.0.1:5001/submit \
    -H 'Content-Type: application/json' \
    -d '{"text":"This is a test submission for rate limit testing purposes only.","creator_id":"ratelimit-test"}'
done
```

## Structured audit log

`instance/provenance.sqlite3` stores original content, one appeal per content ID,
and append-only JSON audit events. Decision/status writes and audit writes share
a transaction; an audit failure rolls the change back. Timestamps are UTC ISO
8601. A successful appeal creates a new event while the original event remains
`classified`. There is no API to alter historical events. This is an application
audit trail, not a cryptographically tamper-proof log.

## Verification

```bash
python -m unittest -v
python -m pip check
```

The 21 offline tests pass without credentials or external calls. They cover
known metrics, invalid/NaN model output, exact scoring and rounded boundaries,
all three labels through `/submit`, disagreement, short/missing-signal guards,
JSON errors, limits, persisted decisions, creator checks, duplicate/concurrent
appeals, review-queue evidence, and transaction rollback on audit failure.
Dependency checks report no broken requirements. Live tests separately observed
all three labels and a successful `201` appeal changing status to `under_review`.

The daily limit is configured in source; the rapid-request test exercises the
minute limit rather than claiming to have run a full-day traffic experiment.

## Known limitations and deployment changes

- A repetitive poem or tightly structured non-native/academic passage can be
  falsely flagged because low sentence variation resembles the structural proxy
  for AI. The semantic signal can share the same bias. Appeals and uncertainty
  reduce harm but do not establish fairness.
- Edited AI text can acquire irregular rhythms and personal details; the live
  remote-work example already demonstrates weak human-leaning evidence for an
  AI-origin test case. Mixed authorship is not reliably separable.
- An explicit AI disclaimer is an easy positive test, and recognizable Poe is an
  easy human test. Humans can quote AI disclaimers and models can quote humans.
  Neither sample establishes generalization or identifies the submitting author.
- Short poems, abbreviations, unusual punctuation, and non-English writing are
  poorly represented by the tokenizer and English-focused semantic prompt.
  Structural coefficients and cutoffs are not learned from validated data.
- Submitted instructions can still influence the model despite prompt isolation.
  No detector result should automatically sanction a creator.

Before deployment, evaluate independently sourced writing across genres and
languages, measure false-positive rates by group and length, and calibrate scores
on held-out data. Add real session-based identity, restricted reviewer access,
human appeal resolution, shared limiter storage, and a data retention policy.

## Spec reflection

The plan made signal direction, the 70/30 formula, exact labels, and the
insufficient-evidence rules explicit before coding. That prevented a provider
failure from masquerading as a neutral second opinion and made the boundary and
appeal tests concrete instead of checking only that endpoints returned JSON.

One implementation change was the rounding order. The original plan classified
full-precision scores and rounded only the response; review showed that a hidden
0.84999 could display as 0.8500 with an uncertain label. The implementation now
rounds first and classifies the displayed value, with a regression test and an
implementation note in planning.md. This changes only the tiny rounding boundary
and keeps the API's score and label consistent.
